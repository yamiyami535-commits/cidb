# Hosted OCR deployment templates

These are Linux VM templates for the existing FastAPI application. They do not
contain a production hostname, certificate, secret, firewall rule, or portal
host configuration. Obtain those values from the infrastructure owner before
installing the templates.

## Runtime layout

The examples use `/opt/cidb-ocr` for the deployed `ocr/` directory,
`/etc/cidb-ocr/ocr.env` for environment settings, and `/var/lib/cidb-ocr` for
the service account's persistent writable home/cache. Change the unit paths if
your deployment uses a different layout. The service runs as `cidb-ocr`, binds
Uvicorn only to `127.0.0.1:8000`, and starts one worker so PaddleOCR is not
loaded multiple times into memory. Do not use Uvicorn `--reload` in production.

## Install and enable systemd

1. Install Python 3.10–3.12 and system packages required by the pinned OCR
   dependencies. Deploy this directory to `/opt/cidb-ocr` and create the
   virtual environment there.
2. Create the dedicated `cidb-ocr` account and persistent writable home at
   `/var/lib/cidb-ocr`. Ensure it can read the application and write its model
   cache. The first model initialization may need outbound network access to
   fetch PaddleOCR models; warm the model before opening production traffic.
3. Install `requirements.txt` in `/opt/cidb-ocr/.venv`. Review compatibility
   of the pinned PaddlePaddle build with the VM's Python version and CPU/GPU.
4. Create `/etc/cidb-ocr/ocr.env` from `../.env.example`, set the approved OCR
   thresholds, and restrict the file to root and the service account. The
   committed systemd unit uses this file as process environment; it does not
   require a `.env` file in the application directory.
5. Copy `cidb-ocr.service.example` to
   `/etc/systemd/system/cidb-ocr.service`. Replace `/opt/cidb-ocr` and
   `/var/lib/cidb-ocr` if the actual paths differ.
6. Run `sudo systemctl daemon-reload`, `sudo systemctl enable --now cidb-ocr`,
   then inspect `sudo systemctl status cidb-ocr` and
   `sudo journalctl -u cidb-ocr -n 100 --no-pager`.

`Restart=on-failure` restarts the process after failures, and `enable` starts
it after VM restarts. A health check should alert on persistent failures; a
restart policy alone does not prove the model initialized successfully.

## Private HTTPS proxy and network controls

1. Install Nginx (or the approved equivalent) on the OCR VM. Copy
   `nginx-ocr.conf.template`, replace its placeholders with the infrastructure
   private DNS name and certificate paths, validate the config, and reload
   Nginx. The certificate must be trusted by the portal host and match the
   private DNS name configured in the portal.
2. Permit HTTPS to this proxy only from the portal host/network. Keep TCP 8000
   loopback-only and blocked by the VM firewall/security group. Set a strong
   `API_KEY` in the protected OCR environment and configure the same value as
   `OCR_API_KEY` in the portal environment. Do not expose the service to the
   public internet.
3. Allow uploads up to the configured PDF size plus multipart overhead and set
   proxy timeouts above the portal's 180-second OCR timeout.

## Portal Cron2 worker

The portal's `bin/ocr_runner.php` calls the OCR service directly from the
portal host:

```text
POST https://<private-ocr-fqdn>/api/verify-mykad-pdf
X-API-Key: <same secret configured as API_KEY>
Content-Type: multipart/form-data; boundary=<generated by HTTP client>
```

Configure the portal `.env` with `OCR_ENABLED=false` until the service and
database are ready, then set `OCR_SERVICE_URL` to the private HTTPS origin,
`OCR_API_KEY` to the OCR service key, `OCR_CONNECT_TIMEOUT_MS=5000`,
`OCR_TIMEOUT_MS=180000`, `OCR_MAX_FILE_SIZE_MB=8`, and
`OCR_MAX_PDF_SIZE_MB=16`. Do not use localhost when portal and OCR run on
separate machines.

The worker sends the mapped customer name and NRIC, plus either a two-page
`document_pdf` or identified front/back images. It stores only a limited OCR
summary. No RPA request is made; the ticket remains in manual review because
the CIDB-use cross-out, company stamp, and director signature are not yet
machine-checked.

Before enabling the worker on an existing portal database, have the database
owner apply the ticket foundation migrations in order, followed by
`database/migrations/20261027_ocr_manual_review.sql`. This guide does not run
migrations.

## Verify deployment

1. On the OCR VM, check `curl -fsS https://<private-ocr-fqdn>/health`. Repeat
   from the portal host to verify private DNS, firewall access, and TLS trust.
2. Confirm `sudo systemctl is-enabled cidb-ocr` and
   `sudo systemctl is-active cidb-ocr`; check Nginx and systemd logs for model
   initialization errors.
3. Test the service from the portal host with the OCR API key. Check that
   invalid keys are rejected and that oversized requests, OCR timeouts, and
   unavailable OCR return documented errors.
4. Check portal PHP/web ingress limits and timeout settings. The repo does not
   include the hosted portal's Nginx/Apache/PHP-FPM configuration, so these
   settings must be made in the actual hosting environment.
