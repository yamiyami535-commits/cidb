# Cancellation ticket workflow foundation

For an existing database, apply `database/migrations/20261020_ticket_workflow.sql` after the portal's base schema and email migration, then apply `database/migrations/20261021_ticket_attachment_lookup.sql`, `database/migrations/20261022_clog_open_status.sql`, `database/migrations/20261023_ticket_conversation_foundation.sql`, and `database/migrations/20261027_ocr_manual_review.sql` in order. `database/schema.sql` includes them for new databases. Migrations are not run automatically. Do not apply the base schema to an existing database.

## Ticket model

`portal_tickets.workflow_status` is the portal-owned workflow status. It is separate from CLOG's `clog_status`, `cidb_interaction_data.current_status`, and the legacy `portal_requests.status` field used for form RPA results. The workflow currently supports:

`intake_pending` → `needs_information` → `ready_for_ocr` → `ocr_processing` → `ocr_manual_review` or `ocr_rejected` → `ready_for_execution` → `execution_processing` → `completed` / `failed`, with `closed` available for operator closure.

The seeded required scenarios are `cancellation-individual`, `cancellation-company`, and `cancellation-classification-pending`. New CLOG and email candidates enter the classification-pending scenario and its default `unassigned` bucket. Customer type remains `unknown` until verified; the code does not assume every cancellation is an individual case.

`portal_ticket_buckets` are scenario-specific and have one optional default bucket. `assigned_to` references `portal_users`; the new `role` column supports `admin`, `manager`, and `agent`. The migration does not add user-management pages or assignment permissions yet.

Ticket records can hold individual and company data, missing-field lists, source data, attachment references, OCR results, and execution results. CLOG attachment binaries are not copied into PostgreSQL or onto the portal server. Instead, each matching ticket gets a `portal_ticket_documents` row per CLOG filename, including its CLOG email ID, CRM ID, retrieval URL, reference validation, and OCR status/result:

`https://cidb.daythree.net/handler/email_fetch/files/{CRM-ID}/{filename}`

Each path segment is URL-encoded. Empty values and control characters are rejected; filename path separators are rejected, while `/` in a CRM ID is encoded inside its path segment. `reference_status='ready'` means the metadata produced a safe URL; it does not test that the remote file is currently available. Cron1 and the email reader use the extracted CRM ID to find CLOG `emails.uniqid`, then follow `files.email_id` to the filenames. The email reader does not save mailbox attachment bytes. Cron1 rechecks linked CLOG records each run so files added after the original email import can be discovered.

`portal_tickets.clog_crm_id`, `attachment_lookup_status`, `attachment_lookup_checked_at`, and `attachment_lookup_result` explain which CRM ID was checked, when it was checked, whether a matching CLOG email/file was found, and the matched CLOG email IDs. Status values include `not_checked`, `crm_missing`, `no_matching_crm_email`, `no_files`, and `found`.

CLOG `case_status` (`Open` / `Closed`) is source-owned and stored in `portal_tickets.clog_status`. Only `Open` creates a CLOG cancellation ticket or qualifies it for attachment reconciliation. `cidb_interaction_data.current_status` is written by the RPA bot and read by the portal; the portal does not overwrite it. The agreed values are `Pending from Customer`, `Customer Replied - Verified`, and `Customer Replied - Document Reject`. The word `Verified` in the reply status means the customer replied; it is not proof of OCR or document approval.

Backend ticket-detail reads can use `SELECT * FROM portal_ticket_details WHERE id = $1`; it returns the ticket fields plus `documents`, queued `actions`, `assigned_user`, linked `portal_request`, `email_intake`, normalized `interaction_details`, the `email_thread` with messages, and `ticket_history`. Search by CRM ID with `SELECT * FROM portal_crm_details WHERE crm_id = $1`; it aggregates linked threads, tickets, and normalized CLOG records. For CLOG mirror status, join `portal_ticket_interaction_status` by `ticket_id`; it exposes the separate portal `current_status` and source interaction outcome code. Each `actions[]` record includes its own RPA state (`manual_review`, `queued`, `dispatching`, `succeeded`, `failed`, or `uncertain`). The action runner is implemented, but actions remain in `manual_review` unless explicitly queued and dispatch is enabled.

For the field-by-field portal UI mapping, sample queue/detail/CRM queries, JSON response shapes, and frontend display guidance, see the [front-end ticket data mapping](frontend-ticket-data-mapping.md).

To show active CLOG tickets, filter the source status as well as the portal workflow, for example `source_type='clog' AND clog_status='Open' AND workflow_status <> 'closed'`. The ticket table may retain closed source tickets for history. For ticket-list screens, query `portal_tickets` directly with selected columns and filters rather than aggregating every document for every row. The underlying `portal_tickets` and `portal_ticket_documents` tables remain available for list filtering and OCR updates. Apply normal backend authorization before exposing customer data or retrieval URLs to the frontend.

## Current intake behavior

- `bin/cron_runner.php` continues to sync CLOG emails and related rows, but only creates/updates a cancellation ticket when `emails.case_status` is `Open`. It stages missing-information actions; the global opt-in flag determines whether new actions start in `manual_review` or `queued`.
- `bin/email-reader.php` accepts only messages whose subject/body mentions cancellation/pembatalan and an ID/account/registration. It saves an email ticket and the decoded message body, then uses its extracted `CRM` field to match CLOG emails/files. It does not dispatch cancellation RPA.
- The CLOG and email workers stage `request_information` actions in `portal_rpa_action_queue` for incomplete cases. Actions start in `manual_review` while `RPA_WORKFLOW_ACTIONS_ENABLED` is false; with the flag enabled, new intents enter `queued` and are eligible for the opt-in runner. Existing `manual_review` rows are not auto-promoted.
- CLOG attachments are metadata references only; the bytes remain at the existing CLOG file endpoint. The IMAP worker does not extract/save attachments that are attached directly to an incoming mailbox message.
- `bin/ocr_runner.php` is an opt-in OCR-only Cron2 worker. It processes only assigned `ready_for_ocr` tickets whose CLOG status is `Open`, fetches eligible CLOG attachments, and stores a sanitized OCR result. The worker requires the ticket foundation and OCR manual-review migrations, configured OCR endpoint/API key, and mapped name and NRIC. OCR results remain in `ocr_manual_review`; this worker does not call RPA or send customer email.
- `bin/cron2_recheck.php check|run --crm-id=CRM-...` is the scoped Cron2 CLOG attachment refresh. `run` is restricted to one CRM ID, only synchronizes open CLOG tickets classified as individual and assigned to a portal user, and only advances the ticket to `ready_for_ocr` when new files appear after an RPA reply status. The reply status is a trigger only; the OCR and manual-review gates remain mandatory.
- `bin/ticket_review.php classify-individual|approve|reject --crm-id=CRM-... --reviewer=USERNAME` provides the current controlled manual path for individual SIT. The reviewer must be an active portal admin or manager. Approval requires an assigned, open CLOG ticket in `ocr_manual_review`, at least one ready document, and a successful OCR identity comparison for every ready document. Approval records reviewer and timestamp and stages cancellation in `manual_review`; add `--queue-rpa` only when explicitly authorizing queueing. Rejection records the reviewer and reason but does not send an email or change the RPA-owned interaction status.
- `bin/rpa_action_runner.php check|dry-run|run` processes explicitly queued ticket actions. Dispatch is disabled unless `RPA_WORKFLOW_ACTIONS_ENABLED=true`, and `run` additionally requires an HTTPS endpoint. Request-information actions are held if a referenced attachment already exists. Cancellation actions require an assigned `ready_for_execution` individual ticket, an Open CLOG case, OCR identity results on every referenced document, and `execution_result` containing `manual_approval_status=approved`, a non-empty `approved_by`, and `ocr_status=MANUAL_REVIEW_APPROVED`. Human-reviewed `manual_review` OCR results are eligible only after this explicit approval is recorded. The worker never infers approval from OCR alone. It records ambiguous submissions as `uncertain` and does not retry them.
- The RPA hub seeds an active `CIDB` / `cidb_masterbot` scenario when that row is missing: `PlayID=105`, `PlayOrder=1`, `ScheduleName=Cancellation Email Masterbot`, `GroupID=9-1784599526`, `CompanyID=1`, and `BotID=118`. Existing scenario rows are preserved by the hub bootstrap; verify an already-existing CIDB row in `ticket_scenarios` rather than expecting it to be overwritten. A runner must also be registered in `rpa_skillset` for PlayID 105.
- The CIDB request-information Bot_Input uses the supplied `sRequst=Pending Customer Attachment`; the hub also accepts the conventional `sRequest` API alias and writes whichever one is configured in the scenario's Bot_Input allowlist. Cancellation uses `sAction=Email Cancellation`. The hub requires CRM ID, email, customer name, and language for requests; cancellation additionally requires a verified customer type, identification number, and `sOCRStatus`. State, contact number, and filenames are optional when unavailable. Confirm the bot's request-variable spelling and value with the RPA bot owner before enabling live dispatch.
- The portal RPA endpoint is configured as `https://bfmt.duckdns.org/api/external/ticket-insert`. Keep `RPA_BOT_API_KEY` in the deployment environment only; do not put it in source or logs. The RPA bot owner is responsible for direct PostgreSQL writeback of the agreed interaction `current_status` values and CLOG interaction/ticket creation; a scheduler `inserted` response only confirms queueing, not delivery or completion. The verified portal column is `varchar(50)`, which fits all three agreed status values; the portal does not write those values. Verify the bot writes each exact value against the SIT database before relying on it.
- One-page PDFs are treated as cancellation forms: OCR may compare readable identity text, but always requires manual review. Two-page PDFs are treated as MyKad front then back. Image pairs must have filenames identifying `front`/`depan` and `back`/`belakang`. Unknown layouts are sent to manual review. CIDB cross-out, company stamp, and director signature checks are not automated.
- Existing portal form submission remains unchanged until the cancellation-type-specific forms are designed. The migration adds customer-type, contact, language, and company fields to `portal_requests` so that work can be added without changing the legacy form's behavior.
